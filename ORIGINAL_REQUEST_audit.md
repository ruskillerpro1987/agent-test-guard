## Задача

Это НЕ задача на реализацию новой функциональности. Это самостоятельная задача независимого forensic-аудита уже существующего кода. Держи её сфокусированной строго на аудите: правки кода разрешены **только** для устранения дефекта, который ты сам обнаружил и подтвердил воспроизведением — никаких доработок "заодно", никакого продолжения Фазы 2/3/4.

**Проект:** `agent-test-guard` — детерминированный pre-commit гейт и CLI на Rust 2021 (workspace), предотвращающий specification gaming со стороны автономных ИИ-агентов (пропуск тестов, тавтологии, опустошение ассертов, нелегальный мокинг, TOCTOU-подмена файлов).

**Working directory:** `F:\AI\agent-test-guard`

**Integrity mode:** audit-only — прогон существующих тестов не считается доказательством корректности; ты обязан пытаться сломать каждый заявленный инвариант собственными adversarial-тестами, а не доверять зелёному `cargo test`.

**Контекст:** код Фазы 1 (`crates/core`, `crates/ast`) и части Фазы 2 (`crates/rules`: E001, E002, E003) был написан автономным агентом в OpenCode **без** независимой adversarial-ревизии. Полное описание текущего состояния — в приложенном `PROJECT_STATE.md` (положи файл в working directory рядом с этим запросом). Ирония проекта: его единственная цель — ловить хиленькие/поддельные тесты у ИИ-агентов, поэтому его собственные первые 89 тестов должны быть проверены минимум так же строго, как guard проверяет чужой код.

## Requirements

### R1. Независимая верификация криптографического ядра (`crates/core`)
Не доверяй `canonical_test.rs` / `crypto_test.rs` / `schema_test.rs` / `ratchet_test.rs` как единственному доказательству. Обязан:
- Сверить вывод RFC 8785 канонической сериализации в `canonical.rs` с официальными примерами из самого RFC 8785 (порядок ключей, нормализация чисел, экранирование) на минимум 5 собственных нетривиальных JSON-документах (вложенные объекты, unicode-ключи, числа с плавающей точкой, отрицательные числа, пустые массивы/объекты).
- Сверить `crypto.rs` (BLAKE3, Ed25519) с официальными test vectors по ссылкам выше — минимум по 3 вектора на каждый алгоритм.
- Протестировать `ratchet.rs`: попытаться сконструировать сценарий, где набор тестов реально уменьшился или тест был переименован/удалён, но манифест **без** валидной Ed25519-подписи `--allow-shrink` всё равно проходит проверку. Задокументировать успех/провал попытки обмана.

### R2. Независимая верификация AST-фингерпринтинга (`crates/ast`)
- Написать минимум 5 собственных adversarial-примеров тестового кода (TS, TSX, Rust), которые **симантически** пусты или тавтологичны, но синтаксически замаскированы (например: обёрнутый в лишние скобки/промежуточные переменные `assert!(true)`, ассерт на переименованную, но идентичную по семантике конструкцию, дублирующий существующий тест 1:1 с переименованными идентификаторами). Проверить, ловит ли `fingerprint.rs` их как структурно идентичные/пустые, или пропускает.
- Проверить fault-tolerance парсера на намеренно битом/неполном исходном файле (незакрытая скобка, смешанные кодировки, BOM) — должен быть явный отказ с диагностикой, а не тихий пропуск файла.

### R3. Независимая верификация правил E001–E003 (`crates/rules`)
Для каждого правила — не запускать существующий `*_test.rs`, а самостоятельно написать минимум по 3 "живых" попытки обхода:
- **E001 (anti-skip):** менее очевидные формы пропуска — вложенный `describe.skip` внутри непропущенного набора, условный `#[cfg_attr(test, ignore)]`, динамическое `.skip` через переменную, а не литерал.
- **E002 (anti-tautology):** тавтология через промежуточное вычисление (`let x = compute(); assert_eq!(x, x)`), сравнение через константу, вычисленную из того же значения, `assert!(1 == 1 || complex_condition)`.
- **E003 (anti-hollowing / assertion floor):** тест с ассертом, который синтаксически валиден, но не проверяет ничего значимого (например, ассерт на тип, а не на значение), тест с ассертами внутри недостижимого кода (после `return`/`panic!` до него).
Зафиксировать по каждой попытке: поймал ли guard обход, если нет — это дефект с приоритетом Critical.

### R4. Замер реального бюджета <25ms
Задокументированный инвариант — Tier A проверка укладывается строго в 25ms на типичном коммите (<50 тестовых файлов). Не принимать это на веру:
- Собрать релизный бинарник (`cargo build --release`).
- Сформировать реальный staged-коммит из 50 тестовых файлов правдоподобного размера (можно сгенерировать синтетически, но реалистичного по структуре AST).
- Замерить latency инструментом типа `hyperfine` (или эквивалентным методом с несколькими прогонами и warm-up) и приложить сырые числа (min/max/mean) в отчёт.

### R5. Границы моков (Tier 1/2/3) — если E004 уже присутствует в коде на момент аудита
Если `anti_mock.rs` уже реализован (см. актуальный `PROJECT_STATE.md` перед стартом — на момент написания этого ТЗ был "в процессе"): написать реальный E2E-тестовый сценарий с замоканным internal IPC/route stubbing и подтвердить, что скомпилированный CLI-бинарник (не юнит-тест уровня кода) реально завершается с ошибкой. Если E004 ещё не реализован — зафиксировать это как открытый пункт, не пытаться реализовать его в рамках этой аудиторской задачи (это отдельная задача).

## Acceptance Criteria / Формат отчёта

Отчёт должен строго отделять факты от интерпретации и иметь вид:

```
=== INDEPENDENT AUDIT REPORT: agent-test-guard (pre-Phase-2.4 baseline) ===

СВОДКА: <1-2 предложения>

R1 — Криптографическое ядро:
  Ed25519 vs RFC 8032: PASS/FAIL (какие векторы использованы)
  JCS vs RFC 8785: PASS/FAIL (какие случаи проверены)
  BLAKE3 vs official vectors: PASS/FAIL
  Ratchet anti-shrink bypass attempt: ПОЙМАН / ПРОШЁЛ ОБМАН (если прошёл — Critical)

R2 — AST fingerprinting:
  <по каждому из 5 adversarial-примеров: поймано/пропущено>
  Fault-tolerance на битом коде: PASS/FAIL

R3 — Правила E001-E003:
  <по каждой из 3+3+3 попыток обхода на правило: поймано/пропущено>

R4 — Латентность:
  Замеренные min/max/mean на 50 файлах: <числа>
  Соответствие бюджету <25ms: PASS/FAIL

R5 — Mock boundary (если применимо): PASS/FAIL/NOT_APPLICABLE

НАЙДЕННЫЕ ДЕФЕКТЫ (только подтверждённые воспроизведением):
  [Critical/High/Medium/Low] <описание> — файл:строка, шаги воспроизведения, что исправлено (если исправлено самостоятельно в рамках R1-R5)

VERDICT: BASELINE TRUSTWORTHY (все R1-R5 пройдены либо найденные дефекты исправлены и переверифицированы)
    или
VERDICT: BASELINE NEEDS REWORK (есть неисправленные Critical/High дефекты — перечислить, что именно блокирует переход к Фазе 2.4)
```

Отчёт отправить пользователю напрямую (или через `send_message` родительскому агенту, если запуск идёт через оркестратор) — не прятать найденные дефекты внутри "всё прошло успешно", даже если большинство проверок PASS.
